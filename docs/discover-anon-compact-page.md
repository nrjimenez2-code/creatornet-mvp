# Checked anonymous compact pages

Existing anonymous feed pagination makes two sequential Data API requests: a fresh anonymous-identity claim lookup, then an owned compact-page read. Migration `20260916064728_discover_anon_compact_page.sql` adds a private wrapper that performs both reads within one database statement. It does not cache claims or change the existing functions.

`discover_anon_compact_page_v1(uuid,uuid,bigint,integer)` accepts a session ID, a server-verified anonymous UUID, offset and limit. It rejects any present identity claim with `CN001`, delegates ownership/expiry/page bounds to `discover_compact_page_v1`, and returns `{anonymousClaimChecked:true,page:<unchanged compact page>}`. Null anonymous identity also fails closed; invalid bounds retain `22023`. It is STABLE, SECURITY INVOKER, has an empty fixed search path and is executable only by service_role. All table/function names are explicitly qualified. No identity, session, event, payment or inventory writes are performed.

The caller must still verify Auth and the anonymous HMAC. The UUID parameter is not a public authentication mechanism. An application flag such as `DISCOVER_ANON_PAGE_ENABLED` must default off and gate only explicitly existing-session requests when the existing compact/page-inventory paths are enabled. Sessionless creation, authenticated viewers, global `discoverIdentity`, events and payment/access routes retain their current checks. An unresolved anonymous page candidate must never enter a creation or unchecked legacy read path. Require the exact `anonymousClaimChecked:true` marker before rendering; malformed/missing markers, missing functions and privilege failures must fail closed. Recursive skipping of fully hidden pages must keep the checked page loader.

Preserve wire behavior: a valid unclaimed actor's successful page returns its existing token, no replacement cookie, unchanged items/cursor and private/no-store caching. A claimed token used with an old session returns the same generic HTTP 410/error code, without a new cookie or actor token. Replacement cookie/token issuance still occurs only through the normal successful sessionless refresh. Auth failures remain 503; route bounds remain 400; missing/expired/wrong-owner sessions remain 410. The fresh inventory is still filtered by the existing application moderation/sell-readiness mapper. Signed/private media locations, access checks, purchase verification and Stripe behavior are untouched.

## Validation and rollout

The focused database suite is `__tests__/discover-anon-page-database.test.ts`. It executes this migration plus the real existing compact/inventory migrations in an isolated in-memory PGlite database. Coverage includes owner/cursor parity, explicit checked marker, effective PUBLIC/anon/authenticated denial, invoker/stable/search-path metadata, null/missing/foreign/expired rejection, bounds, a claim appearing after an earlier successful read, unchanged account-owned legacy page access, current moderation/media projection, dependency-permission failures and no writes. The local focused run passed one suite / nine tests in 8.881 seconds; this is database-function verification, not an application or capacity result.

PGlite tests are sequential, not a two-connection production Postgres concurrency proof. The wrapper reads within a STABLE statement snapshot: a claim committed before the read must reject; an overlapping claim can serialize after the read snapshot. Before staged enablement, verify that ordering with two isolated real Postgres connections, including claim-commit before read, migrated account ownership, and overlapping read/claim. No local psql/postgres/initdb/docker runtime was found during this implementation; this explicit concurrency check remains open. Do not add row/advisory locks or identity caches to avoid the test.

1. Complete application resolver/flag/marker/recursive-path implementation and route tests, including exact 410/no-cookie and subsequent-refresh rotation behavior. Run the existing identity, moderation, private-media, payment and ranking checks.
2. Apply the migration to staging only with the flag off; verify function definition, grants, dependencies and database advisors. No live migration or flag enablement is performed merely by adding these files.
3. Complete the isolated real-Postgres transaction-order checks, then enable the flag only on the staging branch. Repeat bounded session-reuse comparisons with the same client/transport/SQL/resource measurements and exact cleanup.
4. Disable the new flag to restore the original fresh-claim lookup plus page RPC if needed. The old functions remain available. Production requires separately authorized rollout after measured evidence.

Removing one ordinary round trip does not establish a latency percentile improvement, eliminate every transport outlier, or prove 1,000/10,000-user capacity. SQL interval means, API latency percentiles and resource headroom remain distinct measurements.
